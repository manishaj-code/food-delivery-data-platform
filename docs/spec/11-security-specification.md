# 11 — Security Specification

Covers FR-130 – FR-136, NFR-009.

> **No secrets may be committed to Git.** This includes AWS access keys, Redshift/PostgreSQL passwords, Airflow admin passwords, Fernet/secret keys, `.env` files, `terraform.tfvars`, and Terraform state. A commit containing a secret must be treated as a leak: rotate the secret first, then remove it from history.

---

## 1. Threat Model (portfolio scope)

| Asset | Threat | Primary control |
|---|---|---|
| AWS account | Leaked access keys | No static keys in repo/CI; OIDC; local profiles only. |
| Redshift data | Public endpoint scanning / credential theft | SG CIDR allow-list, TLS, Secrets Manager, read-only BI user. |
| S3 data | Public exposure | Block Public Access, TLS-only policy, least-privilege roles. |
| Secrets | Accidental commit / logging | `.gitignore`, `.dockerignore`, masking in logs, review checklist. |

The data is synthetic (fake names/emails at `example.com`), which limits impact, but controls are implemented as if it were real.

## 2. IAM and Least Privilege

- One role per purpose (pipeline, Redshift S3 read, GitHub deploy) — spec 09 §3.3.
- Actions and resources are explicit; no `"Action": "*"` with `"Resource": "*"`.
- S3 permissions scoped to the project bucket; Redshift COPY role scoped to `processed/*` read only.
- CloudWatch `PutMetricData` limited by namespace condition.
- Secrets Manager read limited to the specific secret ARN.
- The deploy role trust policy is limited to this repository and the `dev` environment/`main` branch.
- **Review checklist** (performed in Phase 13): no wildcard admin, no inline user keys, conditions present where supported, resources ARN-scoped.

## 3. Secrets Management

| Secret | Local mode | AWS mode |
|---|---|---|
| Warehouse password | `REDSHIFT_PASSWORD` in untracked `.env` (local Postgres dev password) | Secrets Manager secret (`REDSHIFT_SECRET_ARN`), generated by Redshift (`manage_admin_password`) |
| AWS credentials | Not needed | Developer's AWS CLI profile/SSO (`AWS_PROFILE`), mounted read-only |
| Airflow admin password, Fernet key, API secret key | `.env` (untracked) | Same (Airflow runs locally) |
| Power BI reader password | n/a | Created manually or in Secrets Manager; entered in Power BI; never committed |
| GitHub → AWS | n/a | OIDC short-lived tokens — no secret stored |

Secrets are read once through `src/common/config.py` / `src/common/secrets.py`; config objects mask secret fields in `repr`/logs (`SecretStr`-style wrapper).

## 5. GitHub Actions OIDC

- IAM OIDC identity provider for `token.actions.githubusercontent.com` (Terraform, spec 09).
- `deploy.yml` requests `id-token: write` and uses `aws-actions/configure-aws-credentials` with `role-to-assume`.
- Trust policy conditions: `aud = sts.amazonaws.com`, `sub = repo:<owner>/<repo>:environment:dev` (apply) — no other repo/branch can assume it.
- `ci.yml` needs no AWS access at all.
- Repository settings: no `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` secrets exist.

## 6. AWS Credentials

Never stored in: GitHub, the Git repository, Docker images, source code, or a committed `.env`. Local AWS mode uses the developer's `~/.aws` profile mounted read-only (`:ro`) into containers at runtime, or SSO.

**Sandbox account (A-21):** the sandbox's temporary credentials (access key, secret, session token) are placed only in a local named profile (`~/.aws/credentials`, e.g. `[food-delivery-sandbox]`) and refreshed when the session renews. They are never put in GitHub secrets. When the sandbox does not allow creating the GitHub OIDC provider (`create_github_oidc = false`), Terraform is applied from the developer machine and `deploy.yml` is not run against the sandbox (spec 09 §3.3.1).

## 7. S3 Security

Block Public Access (all 4), SSE-S3 encryption, bucket policy denying non-TLS requests, bucket-owner-enforced object ownership (ACLs disabled), prefix-scoped IAM, lifecycle expiry of transient/quarantine data.

## 8. Redshift Credentials and Access

- Admin credentials only in Secrets Manager; fetched at runtime; never logged (log messages show host/db/user only).
- TLS (`sslmode=require`).
- Security group restricted to `allowed_cidr_blocks` (developer's public IP /32). Never `0.0.0.0/0` (Terraform variable validation rejects it).
- `powerbi_reader` has `SELECT` on views only.
- SQL is parameterised; identifiers (schema) come from validated config (regex `^[a-z_][a-z0-9_]*$`).

## 9. Repository Hygiene

### `.env.example`
Committed; every variable from §4 with **placeholder** values only (e.g. `REDSHIFT_PASSWORD=change-me-local-only`) and comments explaining local vs AWS mode.

### `.gitignore` (minimum)

```text
.env
.env.*
!.env.example
*.tfvars
!terraform.tfvars.example
*.tfstate
*.tfstate.*
.terraform/
tfplan
lake/
data/generated/
logs/
airflow/logs/
__pycache__/
.pytest_cache/
.ruff_cache/
.coverage
htmlcov/

```

### `.dockerignore`
Excludes `.env*`, `.git`, `lake/`, `data/generated/`, `terraform/.terraform`, `*.tfstate*`, `*.tfvars`, caches, `docs/` (not needed at runtime).

## 10. Docker Secrets

- Images contain no secrets; configuration injected at runtime via `env_file: .env` (local) and mounted AWS profile.
- Containers run as a non-root user.
- Base images pinned; no `latest` tags.
- Compose secrets (`secrets:`) are not needed for local-only dev; documented as the upgrade path.

## 11. Logging Hygiene

- Config and connection objects implement masked `__repr__`.
- A test asserts that the configured password never appears in captured logs (FR-135).
- Error messages from DB drivers are logged, but connection strings are never built with passwords embedded in logged strings.
